# Parsing MATPOWER cases, 2026-11-05

Phase O2's third CPU target, chosen from [`profile-2026-11-04.md`](profile-2026-11-04.md):
reading a case file took 25–48% of a single DC or fast-decoupled run and 15–21% of a single
Newton run, by that profile's samples. As for every O2 change, the reader's results must not
change: the same `Case` from every file, and the same error, line and message for every
malformed one.

## Setup

| | |
|---|---|
| Code | The `dev/parsing` branch, at the commit that adds this record, against `main` before it (`510aff1`) |
| Machine and system | As in the earlier records: Intel Core i7-14700K (28 hardware threads), Ubuntu 24.04.3 under WSL2, Rust 1.97.1, release profile |
| Parse times | The `profile_pf` example's new `parse` workload (`Case::from_path` alone: reading the file, decoding and parsing it, and `Case::validate`) on each of the 78 normalized cases, repeated for 1 s and at least once, with `main`'s binary and this branch's run back to back; per-case times in [`parsing-2026-11-05.csv`](parsing-2026-11-05.csv) |
| Single runs | `profile_pf`'s `parse`, `dc`, `fdxb` and `nr` workloads on the profile's four cases, each repeated for 4 s, both binaries back to back |
| Criterion | `cargo bench -p powerflow --bench dc_power_flow -- parse`, against a baseline saved on `main` |

`profile_pf` prints milliseconds to three decimals, so the times of cases under 20 KB (a few
microseconds) are coarse; the figures below use the 39 cases of 20 KB or more. Repeated runs of
a case agreed within about 5%, except on the largest cases, which fit only 7–8 runs in 1 s:
`main` read case_ACTIVSg70k in 131, 142 and 147 ms on three runs.

## Where reading a case spent its time

A profile of the `parse` workload on `main` (case2383wp and case_ACTIVSg70k, about 4,000
samples each, attributed to source lines with `addr2line`):

- **The reader's own code, about 50%** (the inlined reader 27%, `strip_line` 16%, and `memchr`
  splitting lines 7%). The largest single part, 22–24%, was the loop in `find_code` that steps
  through each line character by character, decoding UTF-8: every line went through it for
  `strip_line`'s comments and continuations, and every matrix line again for `collect_until`'s
  closing bracket. Splitting matrix rows on `char::is_whitespace` was about 10% more.
- **Allocation and copying, about 20%.** About half of it was each matrix row's values growing
  one push at a time (reallocating at 4, 8 and 16 values for a 13-column row): sizing rows up
  front saved about 10%.
- **Float parsing, 15–17%** (`str::parse::<f64>`). It stays: it's what makes the doubles the
  same.

## The changes

| Commit | case2383wp | case_ACTIVSg70k |
|---|--:|--:|
| `main` | 2.75 ms | 130 ms |
| 1. Scanning lines by bytes | 2.62 ms | 126 ms |
| 2. Tokenizing matrices by bytes, rows sized like the first | 2.33 ms | 108 ms |
| 3. Ruling out plain lines before scanning them | 1.83 ms | 84 ms |

1. **Scanning by bytes.** Every byte `find_code` stops on (quotes, comment markers, dots,
   brackets, separators) is ASCII, and in UTF-8 an ASCII byte only ever encodes that character,
   so a scan by bytes finds the same indices. A character outside ASCII reaches the callers'
   predicates as each of its bytes (all at least 0x80), which they treat as they treated the
   character. The gain was small: decoding wasn't the cost, stepping through every byte was.
2. **Tokenizing by bytes.** A segment that's all ASCII, as matrix rows are, splits in one pass
   on the ASCII characters `char::is_whitespace` accepts (vertical tab included, which
   `u8::is_ascii_whitespace` leaves out), commas and `;`; any other segment keeps the character
   split, so a non-breaking space from a Latin-1 file still separates values. Each row after the
   first reserves the first row's width, which alone was about 10%.
3. **Ruling out plain lines.** Most lines hold nothing the scans stop on. A check over 64-byte
   chunks without an early exit, which the compiler vectorizes, rules those lines out first:
   without a quote, `strip_line` can only stop at `%`, `#` or three dots in a row (which always
   leave two in a row within one chunk), and `collect_until` only at its closing bracket. Other
   lines are scanned as before.

No new dependencies and no `unsafe`; `str::parse::<f64>` still converts every number.

## The same results, checked

- **A snapshot** (temporary, not committed, as in the two earlier O2 changes): a hash of the
  `Debug` text of `Case::from_bytes`'s result for 18,749 inputs, with 7,714 distinct outcomes:
  every `.m` file in MATPOWER 8.1 and the normalized cases (its 2,622 files include MATPOWER's
  own code, which exercises the reader's errors), 150 random byte replacements, insertions,
  deletions and truncations of each case under 60 KB (bytes from 0x80 up included, which send the
  file through Latin-1 decoding), and every truncation of ten inputs written for the byte paths.
  The hashes matched `main`'s exactly after each commit.
- **New syntax tests:**
  - **Separators:** every kind of whitespace separates matrix values (ASCII, including
    vertical tab, and Unicode, such as U+00A0, U+3000 and U+0085), and other characters outside
    ASCII stay part of a value.
  - **Next to the syntax:** text outside ASCII beside dots and quotes, for example `é'`, which
    is a transpose.
  - **Continuations:** a continuation at every offset around the 64-byte chunks.
  - **A quirk:** the existing behaviour that only a precheck holding the quotes keeps (below).
  
  All pass on `main` as well. Seven planted bugs were each caught by a test (omitting vertical
  tab, sending non-ASCII segments down the byte path, a dot run that non-ASCII bytes don't
  reset, ASCII-only letters before a transpose, a precheck without dot pairs, without `"`, or
  without the closing bracket).

## Results

### Every case

| | `main` | This branch |
|---|--:|--:|
| All 78 cases | 527 ms (190 MB/s) | 343 ms (293 MB/s), **1.54×** |
| Cases of 20 KB or more | | median **1.51×**, 1.29–1.76× |
| case2383wp | 2.81 ms | 1.85 ms, 1.52× |
| case9241pegase | 14.1 ms | 10.4 ms, 1.36× |
| case_ACTIVSg70k | 147 ms | 91 ms, 1.62× |
| case_SyntheticUSA | 163 ms | 105 ms, 1.55× |

The spread between cases is real, since repeated runs reproduce it (case6470rte 1.68–1.71×,
case2868rte 1.29–1.35×), but not explained. Both files have the same tables and row layout, the
same share of values with 15 or more digits (18–19%) and the same three lines that miss the
prechecks. `main` reads them at 5.8 and 5.4 ms per MB, and this branch at 3.4 (case6470rte) and
4.1 (case2868rte).

**The criterion benchmark** reads MATPOWER's own case2383wp, not the normalized one: 2.19 ms on
`main`, 1.63 ms here (**1.35×**). The normalized file is 550 KB to the original's 341 KB, since
Octave writes every value at 17 significant digits (`0.94999999999999996` for `0.95`).

### Single runs

Timed separately, reading the case is a larger share of a run than the profile's `Parse`
column showed: that column counted samples in the reader's own code, and its allocations fell
under `Alloc`.

| Case | Reading the case | Its share of a DC run | DC | Fast-decoupled (XB) | Newton |
|---|--:|--:|--:|--:|--:|
| case2383wp | 2.75 → 1.87 ms | 61% → 54% | 1.30× | 1.09× | 1.11× |
| case9241pegase | 14.2 → 10.5 ms | 48% → 41% | 1.17× | 1.13× | 1.05× |
| case_ACTIVSg70k | 131 → 84 ms | 49% → 39% | 1.23× | 1.05× | 1.12× |
| case_SyntheticUSA | 153 → 98 ms | 48% → 39% | 1.25× | 1.15× | 1.08× |

A run should save the time reading saves. DC runs saved 9–19% more than that on all four
cases, which wasn't investigated. The longer runs are noisier (case_ACTIVSg70k's fast-decoupled
run saved 17 ms and its Newton run 72 ms, against 47 ms saved in reading), since only a handful
of them fit in 4 s.

## What's left, and a finding

- **Float parsing is now the largest part,** about 28% of reading case_ACTIVSg70k, then the
  matrix tokenizer about 19%, the C library (reading the file, allocation and copies) about 15%,
  the prechecks about 9%, and UTF-8 validation and `Case::validate` about 2% each. Going further means fusing the passes
  over each line into one, or a float parser of our own, which would have to be shown to give
  `str::parse`'s doubles on every input. Neither was tried.
- **A quirk the prechecks had to keep:** a quote that starts a string never reaches
  `strip_line`'s dot counter, so dots separated only by strings count as one run, and
  `mpc.note = 1 ."x"."y".` ends at the third dot, inside the second string. MATLAB wouldn't read a
  continuation there. It's kept, as O2 changes no results, and a test now pins it so that
  changing it is a deliberate choice.
